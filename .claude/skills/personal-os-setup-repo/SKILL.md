Keep both: dropping the branch-`push` trigger removes CI before a PR exists (the standing expectation is that a push runs CI rather than waiting for the PR), and dropping `pull_request` removes CI for **fork PRs** — a fork's branch lives in the contributor's repo, so no push event fires here (this repo has real fork PRs; check `gh pr list --state all --json author,headRepositoryOwner` before assuming otherwise). `on:` cannot express "fork PRs only", so the gate belongs on the job: `if: github.event_name == 'push' || github.event.pull_request.head.repo.full_name != github.repository`, and anything that needs the PR payload (the PR-title lint) moves into its own small `pull_request` workflow with `types: [opened, edited, reopened]` — deliberately without `synchronize`, which would re-fire it on every push. Push-triggered runs still appear in the PR's checks (check runs attach to the head commit), so push-only genuinely covers own branches. Accepting the duplication as-is is a legitimate choice: it costs runner minutes and nothing else.

## Skill library: audit & cleanup (recurring ask — "what skills do I have / which can I delete?")
- **Provenance comes from bookkeeping, never from the directory a skill sits in**: `.bundled_manifest` = addon-shipped, `.hub/lock.json` = registry-installed, the two chezmoi trees = git-managed, everything else = live-only (**the only class that is locally deletable**). **Both bookkeeping sources under-report, so prove a name live-only before calling it deletable**: the addon's own tree is `~/.hermes/hermes-agent/skills/<category>/<name>/` and `.bundled_manifest` does not list all of it (`hermes-agent`, `claude-code`, `hermes-agent-skill-authoring` are shipped there yet absent from the manifest, while `hermes skills list` still prints `N builtin` = 0). Check it in one pass: list both trees, then `diff -rq <addon-copy> <live-copy>` — a name present in both is addon-shipped, and differing files mean the live copy is a frozen override the addon sync skips forever (so `hermes skills list-modified` reporting "everything tracks upstream" says nothing about those names). Sizes come from `du -sk <dir>`, demand from `.usage.json` (`use_count`, `last_used_at`, `state`); a category dir (a `github/`-style folder) says how something was filed, not who updates it.
- **Answer with a per-track table that names the owner of each row and mark only the deletable ones.** Deleting a git-managed name locally is a no-op — the next `make skills-deploy` (or the repo) restores it — so say that instead of deleting. `make skills-status` IS the authoritative duplicate list ("live copies duplicating a git-managed name (deploy replaces them; remove the live copy)"); never hand-diff trees to find duplicates.
- **Order is deploy → verify → delete.** A "duplicate" is the ONLY live copy while that name is still `MISSING` at its deploy destination, so deleting first drops the skill from the index entirely. `make skills-deploy` refuses on ANY `DIFFERS` → settle the per-file direction calls first; `SKILLS_FORCE=1` is the sanctioned overwrite and is safe only once every remaining `DIFFERS` is a "git should win" case. After deleting, grep the surviving `**/SKILL.md` for the removed filenames — a live SKILL.md that pointed at a deleted `references/` file keeps a dangling pointer until the next deploy replaces it with the repo version.
- **`hermes curator prune` only archives, and `hermes curator purge` is DISABLED at the default `curator.archive_ttl_days: 0`** → emptying `.archive/` is a manual `tar` + `rm` of explicit paths; never present a curator command as the deleter.
- **Cleanup is destructive-action territory: list the exact paths, then ask — at every step, not once for the whole plan — and a clarify "yes" does not cover the terminal's own approval prompt.** One destructive step per gated call: a batched backup-then-delete loses the backup too when the prompt times out, and the block forbids re-running that command. **A backup is not a default step** — he answers a proposed one with "no need to backup", so when git holds the content (a tracked skill file, a file on a pushed branch, a copy the deploy source mirrors) say in one clause that git history is the copy and skip the step; keep the tarball (`~/.hermes/backups/cleanup-<what>.tar.gz`, outside the repo) for live-only content with no git copy, offered rather than run unbidden. Then verify the names are gone AND the neighbouring files intact.
- **A removal the USER performed leaves no trace — ask what changed before hunting a culprit.** The curator ledger records only curator/agent mutations, so skills the owner deletes by hand vanish from the store and from `hermes skills list` with no ledger entry, no log line and no hub-action record; the same is true of `hermes skills disable`, which keeps the files, drops the skill from the index and still shows up as `DIFFERS`/duplicate in the probes above. When a count differs from an earlier probe in the same session, ask the user first — a phantom-culprit investigation across ledger, logs and plugins burns calls and ends in the answer they already knew.
- **Repo copies are the sanitized ones; live copies legitimately keep real values** — so a live→git port must re-scrub on the way in (scan the ported diff for a personal email domain, `/addon_configs/[0-9a-f]{6,}`, real names/chat ids, and match git's own placeholders such as `<repo>_<slug>` / `user@example.com`). Report the scrub: a clean scan is the evidence the public repo stayed clean.
- **Take the counters from the CLI, never by hand-parsing `.usage.json`.** `hermes curator usage` prints one row per skill — origin (`agent` / `bundled` / `hub`), use/view/patch counters and last activity — across every track, which is exactly the demand evidence a prune decision needs. `hermes skills list` ends with `N hub-installed, N builtin, N local — N enabled, M disabled` and marks disabled rows inline (`hermes skills disable` keeps the files and drops only the index entry, which is how the owner silences a skill the curator keeps rewriting). `hermes skills list-modified` answering "No user-modified bundled skills — everything tracks upstream" is the proof the addon side is clean. An `awk` pass over the JSON silently returns zeros on the next schema tweak and sends you chasing a phantom — this has happened twice.
- **A skill's category IS its path** (`tools/skills_tool.py::_get_category_from_path`, first path component): `<root>/<category>/<skill>/SKILL.md` → that category, flat `<root>/<skill>/SKILL.md` → blank, and the `DESCRIPTION.md` in a category dir is just that category's blurb text. It is path-driven, not frontmatter — a name read as `github` only while a copy lived in a `github/` dir, and went blank once only the flat copy remained. Re-file by track: live-only → `mv` between category dirs; git-managed → the repo path *is* the category, so `git mv` in the source tree and re-deploy (moving only the live copy comes back as `MISSING`/`DIFFERS`); the flat shared Track-1 source would need nested dirs **plus** a `makefiles/skills.mk` change, and both agents read that tree. Category also forms the address used in config (`category/skill`), so a rename can invalidate config — and any of it lands only in a NEW session.
- **"Sync the skills" is two syncs — ask which, and answer each separately.** repo↔live is `make skills-deploy` (what `make skills-diff` measures, and what keeps returning once the curator or the learn pass writes the live copy); addon↔bundled runs itself and needs no action when `hermes skills list-modified` reports nothing frozen. Never let the deploy story imply a pending bundled update, or the reverse.
- **A count that moves mid-session is the user or the background review — check mtime before hunting a culprit.** The learn pass writes skills out of the session itself (a new `devops/<name>` skill appeared uncommanded, and the curator re-patched a box skill while a cleanup was in flight), while hand-deletions leave no ledger entry at all. One `stat -c '%y'` on the delta separates the two; ask the user before opening a ledger/log investigation, and expect "it's me".
- **Tidy the leftovers in the same pass.** Deleting a skill leaves its category dir behind (harmless — it holds only `DESCRIPTION.md`), so empty dirs go with the same explicit-path `tar` + `rm`; `.archive/` needs the manual treatment described above.
- **Two skills on one topic are not automatically duplicates — diff them and say which case it is BEFORE pitching a merge.** The tell: one copy carries the procedure (trigger → steps → verification, the runbook) and the other the library/API depth the runbook itself points at (postprocessor internals, script + `references/`); that is a deliberate split, and a merge pitch that skips the diff comes straight back as "why merging? is there a diff?". When it really is one skill in two homes, choose the survivor by MANAGEMENT, not by size: the chezmoi-deployed copy is drift-checked, curator-pinnable and outside the published site, whereas a copy under `docs/` is hand-symlinked (a fresh machine silently has no skill), refused by `skill_manage` (symlink) and PUBLISHED — the properdocs exclude glob protects `src/personal_os_setup/config/**` plus `AGENTS.md`/`CLAUDE.md`, never `docs/`, so confirm from `properdocs.yml` and the built `site/` tree before calling a docs-hosted skill private, and port the runbook into the deployed tree before deleting it — `site/` is gitignored, so the removed page leaves the published site at its next build. **Fold the DELTA, not the file:** read the project's own README/runbook first (the surviving skill's new section is often already sitting there in prose), so the survivor gains a handful of lines — the rules the doc lacks — instead of a duplicate of it; then `make skills-deploy` and re-run `make skills-diff`, where 0 `DIFFERS`/`MISSING` is the proof the index serves the merged skill.
- **Probe the branch's PR state before saying where skill work lands.** `git log --oneline main..HEAD` + `gh pr list --state open` in one pass: a shared checkout can be sitting on an entire unmerged skill track (many commits, no PR at all), so "open a PR" is a different decision there than on a small branch off `main`. Report the count in one line and let him pick — and expect him to answer with the next topic ("let's move to the other repos") rather than with the branch itself. **Fetch first, and count against `origin/main` — never the local `main` ref** (`git fetch origin && git rev-list --left-right --count origin/main...HEAD`; a non-zero LEFT side means the branch is also behind, which is what makes `main..HEAD` overstate the pending work). Ask for the PR in EVERY state, not just open: `gh pr list --state all --head <branch>` — these repos squash-merge and delete the head branch, so a local branch can look like an unmerged track while its content already sits on `main` under one squash commit. Then compare TREES, not logs (`git diff --stat origin/main HEAD -- <the paths the branch was about>`): identical trees plus a MERGED PR means there is no PR left to open — cut a fresh branch off `origin/main` and re-apply only the current change, because a PR from the stale branch lists other merges' files as reverts (`CHANGELOG.md`, `uv.lock`, `pyproject.toml`, another PR's new docs).
- **For a live-only skill the export-vs-keep call is a privacy scan, not a usefulness score.** Export to the repo that owns the subject (add-on knowledge → the add-on repo, repo workflow → that repo) only when the scan is clean — `grep -rInE '([0-9]{1,3}\.){3}[0-9]{1,3}|[a-z0-9.-]+\.(com|fr|net)|/addon_configs/[0-9a-f]{6,}'` (plus a personal email domain), ignoring placeholders like `example.com`/`homeassistant.local`; a skill holding the owner's real LAN IPs, token-in-URL endpoints or live-exposure findings stays live-only and gets `hermes curator pin <name>` (unpinned it is stale at 14d and archived at 30d, and the privacy rule bars its content from a public repo in any form). Demand decides only whether it is worth keeping at all — `hermes curator usage` has the counters, and a skill with real use counts is never a delete candidate merely because no repo backs it. **Where it lands decides when the live copy can go.** A repo-scoped home (`<repo>/.claude/skills/<name>` plus its `.agents/skills` symlink) stays invisible to chat sessions until that repo's `.agents/skills` dir is in `skills.external_dirs` (and the repo root in `trusted_project_dirs`) — so place the files, get that one config line in, and only then delete the live copy: until it is registered, the live copy is the only copy the index serves. Treat a scrubbed/staged export copy as a SNAPSHOT: any edit made to the live skill afterwards has to be re-copied in before the port, or the repo ships the older text.

## Where a new procedure lives: a SKILL, not a docs page
- **A repo-bound runbook is a skill, never a `docs/` page.** Anything under `docs/` is crawled into the published site unless the exclude-glob catches it (see "Published docs" below), and a doc only helps a human who remembers it exists — a skill loads itself at task time, in both agents. Expect the redirect "why keep it in docs? move it to skills" the moment a doc starts describing how to *do* something.
- **Add-a-skill checklist:** create `.claude/skills/<name>/SKILL.md` (frontmatter `name:` + a trigger-shaped `description:`) → `make skills-link` (creates the `.agents/skills/<name>` symlink) → `make skills-check` (must print `OK` for every skill) → add a row to the AGENTS.md Index table → repoint/remove every reference to whatever it replaced, proven with `grep -rn '<old-path>' . | grep -v '^./.git/'` returning nothing.
- Keep the skill lean (~15–20 lines of core content) and agent-facing: where each piece comes from, the gate, the traps. Depth stays in the repo's own docs or the shared chezmoi skills.
- Pick the tier before writing: repo-bound procedure → `.claude/skills/` (this repo, symlinked for non-Claude agents); cross-machine curated → the chezmoi `dot_claude/skills` source + `make skills-deploy`; fast-moving upstream → Track 2 plugin / skills-CLI, never hand-copied into Track 1.

## Sharing third-party agent tooling with BOTH agents (MCP servers + skills)
When the ask is "install <service> for me, both Claude and Hermes must see it, and anything that changes needs approval", the REPO holds the recipe and each agent keeps its native wiring — there is no single shared config file:
- **Skills.** Track 1 = vendored in the chezmoi `dot_claude/skills` source (deployed by `make skills-deploy`). Track 2 = a self-updating Claude plugin (`claude plugin marketplace add <owner>/<repo>` + `claude plugin install <name>@<marketplace>`, stored under `~/.claude/plugins/`). **Do NOT point Hermes at the plugin's cached `skills/` subtree** — the cache path embeds the resolved plugin VERSION (`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/skills/…`) and changes on every update; it is version-scoped, not a stable skills dir. For skills BOTH agents must see, use the vendor's own multi-agent installer instead: **the `skills` npm CLI treats Hermes as a first-class agent** — `npx -y skills add <owner>/<repo> --skill '*' --yes --global --agent hermes-agent` puts the ONE canonical copy in `~/.agents/skills/` and creates a relative symlink into that agent's dir (`$HERMES_HOME/skills/<skill>` for hermes-agent, `~/.claude/skills/<skill>` for claude-code), so scoping to `--agent hermes-agent` never touches the Track-1 `~/.claude/skills` dir that `make skills-deploy` owns. Use ONE mechanism per agent (Claude = the plugin, Hermes = the CLI symlinks) or the agent sees two skills with the same name.
- **MCP servers.** Hermes has a first-class CLI: `hermes mcp add <name> --url <url> --auth oauth` then `hermes mcp login <name>` (or `hermes mcp reauth --all`); tokens persist under `~/.hermes/mcp-tokens/<name>.json`. Config = `mcp_servers:` in `~/.hermes/config.yaml` (HTTP transport is `url:`), shared by BOTH addon containers, and adding a server needs a restart — no hot reload. Claude Code takes its servers from the same plugin, else `claude mcp add` (user scope lives in `~/.claude.json` `mcpServers`).
  - **`hermes mcp add` is NOT idempotent on its own:** when the name already exists it calls `input()` for `Server '<name>' already exists. Overwrite? [y/N]` (default NO) — in a make/CI context that either blocks the recipe on a question or silently cancels. Guard every re-runnable recipe with `hermes mcp list 2>/dev/null | grep -q <name>` → print "already registered — left unchanged" instead of re-adding.
  - **Remote (HTTP) MCP costs no local RAM** — one socket inside the already-running gateway process plus the tool schemas; a *stdio*/npx server spawns a node process per server (~50–80 MB). That is the answer to "does the MCP consume RAM?": quote the config line and, when he wants numbers, the container's own `memory.current` + the gateway's RSS (`ps -eo rss,cmd`) rather than a guess.
- **Gate the writes, and say which layer gates them.** `trust: untrusted` on a Hermes MCP entry routes every write-capable tool through the approval surface; Claude asks per MCP tool by default. Where the service offers both, prefer a scoped API token in `headers:` over an account-wide OAuth grant — the agent container then holds exactly that much power if it is ever popped.
- Ship it as ONE idempotent make target so a fresh machine re-applies it; the repo carries the recipe, the credentials stay in the agent homes.
- **Never let a recipe require BOTH agents.** This repo runs on several machines, so a target that hard-fails on a missing CLI is wrong: guard each half with `command -v <cli> >/dev/null 2>&1`, print `== <Agent>: skipped ('<cli>' not on PATH)` and exit `rc=0`, and expose per-agent targets (`agents-<svc>-claude`, `agents-<svc>-hermes`) plus an umbrella that runs whichever exist. Make the binaries overridable (`CLAUDE ?= claude`, `HERMES ?= hermes`) — `claude` lives in `~/.local/bin`, off `PATH` inside the add-on containers, so the real invocation is `make agents-cloudflare CLAUDE=/config/.local/bin/claude`. Verify the skip paths by running each half with a BOGUS binary name (`make agents-<svc>-hermes HERMES=nope-hermes`) — it exercises the guard without installing anything.
- **Don't ship a `*-check` make target for what the vendors already print.** He asks "do we need it?" and the answer is usually no: `claude plugin list`, `hermes mcp list` and a grep for the approval gate cover it — reference those in the doc instead of maintaining a parallel diagnostic. Keep the ONE assertion that no vendor command shows (the `trust: untrusted` grep) as the last line of the install recipe, where it cannot drift from what was just installed.

- **Renewal is three different mechanisms — say which one applies, because "how does this update?" is the follow-up to every install (Sep 2026):** a **remote HTTP MCP server has nothing to update locally** — the vendor ships it server-side and the tool list is re-read at connect; the only local artifacts are the config entry and the OAuth token, which refreshes itself (`hermes mcp reauth <name>` when stale). **Skills are files**, so the vendor CLI owns renewal: `npx -y skills update -g -y` — scoped to the canonical `~/.agents/skills`, which is safe to run globally precisely because the curated Track-1 copy lives in `~/.claude/skills`. **Claude plugins** renew with `claude plugin marketplace update <marketplace>` then `claude plugin install <plugin>@<marketplace>`; marketplaces also take `"autoUpdate": true`. Ship renewal as an `agents-<svc>-update` target that skips missing CLIs exactly like the install target.
- **After ANY agent-side update, restart the Hermes gateway (`hermes gateway restart`).** MCP connections are established at **startup**, not per session — a gateway up for days keeps pre-update modules and a stale or absent MCP socket, and `hermes mcp list` says so verbatim ("A previous `hermes update` pulled new code but did not restart running gateways"). Treat that line as a to-do and surface it when asked whether an MCP server is running. Skills are read at session start (a new session picks them up); Claude Code needs `/reload-plugins`.
- **Keep the credential out of the committed config: scope a token, reference it by env var.** Hermes resolves `${VAR}` (and Cursor's `${env:VAR}`) anywhere inside an MCP server entry, so the least-privilege form is `headers: {Authorization: "Bearer ${SERVICE_TOKEN}"}` with the value in `~/.hermes/.env` — never a literal in `config.yaml`. Prefer this scoped-token route over an account-wide OAuth grant when the service offers both: it bounds exactly what the agent container holds if it is ever compromised.

## Resuming an in-flight mission (multi-session work)
- **`git fetch --all --prune` BEFORE concluding a file does not exist or that a branch is behind.** Sibling sessions merge PRs into `main` while this checkout sits on an older branch, so the local remote-tracking refs are stale: a `search_files`/`grep` over the working tree (or over the un-fetched `origin/main`) confidently reports "no such file" for a page that has been on `main` for hours, and the stale tree still carries the pre-split version of the doc. Resolve content from the fetched ref, never the tree: `git ls-tree -r --name-only origin/main -- docs/<dir>`, then `git show origin/main:<path>`, and cut the worktree off that ref.
- **Do the branch work in a `git worktree`, not by switching branches under another session.** This checkout carries concurrent Hermes sessions (one sat on a `docs/...` branch while unrelated work was prepared): `git fetch origin && git worktree add -b <branch> /tmp/<wt> origin/main`, then copy the artifact in (`cp <file> /tmp/<wt>/<same/path>`). An untracked artifact stays in the PRIMARY checkout, so it is sitting on whichever branch that session has checked out — stage it explicitly inside the worktree and never with `git add -A`. A worktree has no venv of its own, so run the hooks with the primary checkout's binary — `/config/workspace/personal-os-setup/.venv/bin/pre-commit run --files <paths>` (it picks up the tracked `.pre-commit-config.yaml` from the worktree root); that is how a real pre-commit pass happens without `--no-verify`. `git worktree remove /tmp/<wt>` after the PR merges. **`worktree add -b <branch> … origin/main` makes that branch TRACK `origin/main`**, so a bare `git push` in the worktree is one `push.default` setting away from aiming at main — always push an explicit refspec: `git push -u origin <branch>` (or `git push origin HEAD:refs/heads/<branch>`), and read back `git rev-parse HEAD origin/<branch>` as the proof.
- **The branch he names may not be the branch you are on — read the checkout before pushing it.** Sibling sessions create, rename and switch branches in this shared tree, so a name from your own last report can be stale: `git branch --show-current`, `git status -sb` (tracking `origin/<same>` with no `[ahead N]` means there is **nothing to push** — say so instead of inventing content for that branch), `git branch -vv` for the whole local picture, and `git ls-remote --heads origin <branch>` when you need proof the remote ref exists. Containment is a separate question: `git merge-base --is-ancestor <a> <b>` reliably answers "is <a> in <b>" (it is only *merge status* that ancestry cannot tell you, because these repos squash-merge). When the request conflicts with what the tree shows, state the mismatch in one line and push the branch that actually carries the pending work.
- **Sweeping stale branches: classify by PR state, never by ancestry — and exclude the branch you are working on.** These repos squash-merge, so a merged PR leaves its branch tip a NON-ancestor of `main` (`git merge-base --is-ancestor` calls already-merged work "unmerged"). Authority is `gh pr list --state all --limit 60 --json number,state,headRefName`; missing/gone upstream refs (`%(upstream:track)` = `[gone]`) mean the remote side was already cleaned. A sweep that excludes only `main` deletes the branch of an OPEN PR — exclude `main`, `backup/*`, and every branch with an open PR before running it. For a branch with NO PR, save the commits first (`git branch -f backup/<name> origin/<name>`); branches with a PR are recoverable from `refs/pull/<n>/head` anyway. Restore a wrongly deleted but pushed branch with `git checkout -b <b> origin/<b>` and prove local head == `origin/<b>`.
- The user reopens missions with context-free openers ("So what do you suggest?") that refer to the LAST session's open menu/options — recover that tail with `session_search` (sort=newest, or the @session link from memory) before answering; never ask what they mean when the referent sits in history.
- Re-verify live state at answer time, don't trust last session's snapshot: days may have passed, so before recommending "merge now" run `gh pr list --state all`, `gh pr checks <n>`, and `gh pr view <n> --json mergeStateStatus,mergeable` — PRs merge in the meantime and new ones appear (the user merges fast).
- **Another session may already have made the edit you were asked for.** Several Hermes sessions run against this same checkout, so before touching a file check `git log --oneline -3`, `git status --short` and `git reflog -8` for a commit that already covers it, and grep for the text to be removed. A `patch` returning `no_change` plus *"modified by sibling subagent … after this agent's last read"* means someone landed it: re-read the file, report the real commit/branch state, and say plainly that another session did the work — never re-apply it and never present it as yours.
- **Prove a push with local git, not `gh`** — `gh` sits behind an approval prompt that often times out (BLOCKED = stop; do not retry or rephrase, the same edit routed another way is the same violation). Approval-free proof the branch is on the remote: `git status -sb` shows `...origin/<branch>` with no `[ahead N]`, `git rev-parse HEAD origin/<branch>` returns a single SHA, and `stat -c '%y' .git/refs/remotes/origin/<branch>` mtime ≈ the push time. Note that after an amend/rebase the **PR title is stale** (it is not the commit title) — offer `gh pr edit <n> --title …` instead of assuming the commit retitle followed through.

- **A PR body written early goes stale — re-read it against the FINAL diff before asking for review.** Multi-commit PRs drift away from the description that was written at commit 1: the body advertised a make target that later commits DELETED and claimed a change was "NOT included" when it had since been committed. Before requesting review, re-read `gh pr view <n> --json body` against `gh pr view <n> --json commits,files` and repair with `gh pr edit <n> --body '…'` (single-quoted, no apostrophes, no file needed for a short body). Prove the repair: `gh pr view <n> --json body -q .body | grep -c '<removed-name>'` must return 0 (grep's exit 1 there is a pass, not an error).
- **"Same PR" is a claim to verify, not a destination.** These repos squash-merge and GitHub deletes the head branch, so the local branch left over from a merged PR is stale — pushing it silently creates a NEW remote branch with **no PR attached** (the push output's `[new branch]` line is the tell). Before pushing to whatever PR the user names: `gh pr view <n> --json state,headRefName` plus `gh pr list --state open`. Already merged → branch fresh off `origin/main` (`git checkout -b <new> origin/main`), `git cherry-pick <sha>` so the PR diff is exactly the intended change, push, open one small PR, delete the stray remote branch you created (`git push origin --delete <branch>`), and tell the user plainly that the PR they pointed at was already merged.
- **A dirty tracked file blocks the branch switch, and a cherry-pick of the current HEAD is a no-op that leaves an in-progress state.** `git checkout -b <new> origin/main` refuses while any tracked file differs (`error: Your local changes … would be overwritten`) — stash exactly that path (`git stash push -m "wip: <file>" -- <path>`), then branch, and REPORT the stash as left behind (`git stash list`) rather than keeping it silently. And never run `git cherry-pick <sha>` while HEAD *is* `<sha>` (a failed checkout makes that easy): git enters a cherry-pick that resolves empty — `git cherry-pick --abort` first, then branch and pick.
- **Dropping a stash is a repo-state change behind the same approval gate as commit/push — never bundle it with the read-only proof that makes it safe.** `git stash drop` plus its verification (`git show 'stash@{0}:<file>' | md5sum` against the saved copy, `git stash list` before/after) in ONE command means a timeout costs both: the block forbids re-running that command, so the evidence is lost and the user has to prompt a second time. Sequence it: (1) fire the read-only proof on its own — plain file ops and single `cp`/`tar`/`md5sum`/`find` one-liners pass the gate, while multi-line loops/heredocs/`python -c` — and the `execute_code` tool — time out even when read-only; (2) keep the backup OUTSIDE the repo (`~/.hermes/archive/…` survives container rebuilds, `/tmp` does not); (3) send the gated drop ALONE, and on "prompt me again" re-issue exactly that one command.
- **One topic per PR — and one FILE per PR.** When the user redirects content into another open PR ("push in the same PR"), the earlier PR is left carrying the same file and goes empty once the target merges: move it with `git stash push <paths>` → `git checkout <target>` → `git cherry-pick -n <sha> && git commit` (the base commit exists only on the first branch, so it must travel) → `git stash pop` → `git add` → commit → push, then delete the orphaned branch local AND remote (`git branch -D <b>`, `git push origin --delete <b>`) and say where the commit now lives (`gh pr view <n> --json commits`) — the user may close the redundant PR himself. **Stage explicitly after every `stash pop`**: popped changes are unstaged, so a following bare `git commit` commits NOTHING while the `git push` in the same script still runs.
- **Doc/recipe reduction pass — expect to be asked "what can be reduced or summarized?" and answer with numbers.** What he accepts: the explanation lives in ONE place (a makefile header keeps 2–3 lines + a pointer to the doc, never a duplicate of the doc's prose); ONE full example block, with variants stated as a delta (`swap headers: for auth: oauth`); sections that share a topic merged (updates + credentials); tables with 3–4 facts converted to bullets; optional side sections ("other servers", "removing it") collapsed into a trailing line. Report the result as line deltas (`108 → 84 lines`) and list what you deliberately left untouched — he decides, then approves the push.

## Editing repo files: CRLF + protected agent files
- Repo files are CRLF with NO `.gitattributes` and autocrlf unset → git stores bytes as-is, so a CRLF-preserving surgical edit yields a small diff. Before assuming a CRLF file forces a whole-file diff, check for `.gitattributes` `text=auto`: in a repo that HAS it (ha-addons), any commit re-normalizes the blob → whole-file diff; without it, edit in place and keep the diff clean. The `patch` tool inserts LF lines among CRLF — harmless mixed endings, hooks still pass.
- `AGENTS.md`/`CLAUDE.md` edits hit an agent-instruction approval gate that often times out when you are unattended → the write comes back BLOCKED. Stop and ask the user to say "prompt me again" to re-fire the exact patch; never retry it and never route the same edit through terminal or another file.

## Tests & checks
- `make test` = `uv run pytest tests/unit`; `make pre-commit` = ruff + detect-secrets + yaml/json/toml + uv-lock. **commitizen fires only at git commit-msg stage — `pre-commit run --all-files` does NOT exercise it.** CI runs the identical commands, so a local pass = CI pass.
- `make test-integration` installs real packages — never run locally (CI-only).
- **"`pre-commit` not found" is a FIXABLE environment defect — fix it instead of living on `--no-verify`.** The repo's `venv/` was built where the *host-side* path resolved, so its script shebangs point at a path that does not exist in the agent container (`#!/addon_configs/<repo>_<slug>/…/venv/bin/python3`) and the hook cannot resolve the binary even with the venv activated. Fix once, from inside the container: `rm -rf venv && make install-dev` → uv creates **`.venv`** (its default name — which `scripts/run_tests.sh` already probes first) with container-valid shebangs; prove it with `pre-commit run --all-files`, where every hook must Pass (that run also exercises `uv-lock` and `skills-check`). Expect the install to sync a stale `uv.lock` at the same time — a diff limited to the project's own `version =` line (lock lagging `pyproject.toml`) is a legitimate sync, not dependency drift, and the `uv-lock` hook passes with it; surface it to the user rather than leaving unexplained dirt in the tree. Only if the rebuild is impossible, run the checks by absolute tool path and `git commit --no-verify` / `--amend --no-verify`, stating the bypass in the PR body — never report the hooks as passing.
- **A dirty `uv.lock` is not evidence of an update — check its DIRECTION against `pyproject.toml` pins before committing it.** The dirty copy can be an older resolution from another branch/time, and an entry contradicting an exact pin (`mkdocstrings-python==2.0.8` in pyproject vs `2.0.5` in the lock) makes the file INVALID, not merely stale — the `uv-lock` pre-commit hook (= CI) rejects the commit. Read both sides of `git diff <base>:uv.lock <worktree file>` in the right direction, and expect a mixed file (a newer `click` sitting beside older everything-else) to look plausible at a glance. `uv lock --check --offline` is NOT a validity test: it re-resolves and fails identically for a valid lock when packages are absent from the offline cache, so it proves nothing either way.
- **"I want the latest lock with up-to-date deps" means regenerate, not commit the dirty file**: on the branch run `uv lock --upgrade`, commit as `chore(deps): …` (no release), push, and report which packages moved/left. Say plainly that a manual refresh bypasses Renovate's cooldown — a one-off, not the routine path.
- A malformed packages.yaml entry surfaces as a TypeError at load time; `TestPackagesYaml` only asserts (distro, manager) pairs resolve to real backends.
