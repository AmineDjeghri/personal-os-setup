# 5. Release

Publish verified packages and documentation from a tested `main` revision.

## Automatic release

Merge a releasable change to `main`. `main-release.yml` runs required CI, builds and smoke-checks
artifacts, pushes the version/tag, verifies release assets, publishes the GitHub release and deploys
docs from that exact tag. Docs-only commits do not create a release or deploy docs.
Versions and tags come from [Conventional Commits](3.conventions.md#commit-convention);
do not edit `project.version` or create release tags yourself. The `dev` release flow is retired.

## Manual release and recovery

Use a clean `main` synchronized with origin, an existing development environment and
[GitHub credentials](#credentials). Confirm that the selected source SHA passed required CI:

```bash
RELEASE_SHA=<tested-commit-sha> make release
```

This versions, builds and verifies the wheel/sdist, publishes matching GitHub assets and recovers
an interrupted publication. It changes Git and GitHub; agents need explicit per-action approval.
Manual release does not deploy docs.

| Need                                          | Action                                                                     |
|-----------------------------------------------|----------------------------------------------------------------------------|
| Retry after the release commit/tag was pushed | Rerun with the same `RELEASE_SHA`                                          |
| Publish already built artifacts               | From the clean matching tagged checkout, run `make release-assets`         |
| Retry documentation only                      | Retry the docs job, or run `make deploy-doc-gh` from the clean release tag |
| Run only version/build/tag preparation        | `RELEASE_SHA=<tested-commit-sha> make release-version`                     |

`make deploy-doc-gh` pushes `gh-pages` and needs separate approval. A failed upload leaves a
recoverable draft; matching remote assets are retained, and conflicting bytes are rejected.

## Credentials

For a laptop, log in once:

```bash
gh auth login
```

Targets resolve `GH_TOKEN`, then the existing gh login, then a hidden terminal prompt.
CI supplies its automatic GitHub token as `GH_TOKEN`. Credentials are never printed.

## Release safeguards

- `RELEASE_SHA` must identify the tested source. A retry accepts only that source or its exact
  tagged semantic-release child; only project version, root lock version and changelog may differ.
- Semantic-release builds both archives and smoke-checks the wheel before committing/tagging.
  `release-version` does not publish GitHub artifacts.
- `release-assets` verifies the clean local/remote tag, checks both archives and their installed
  wheel, uploads missing assets to a draft, then downloads and compares the full remote pair before publication.
- Preview errors fail; no releasable commits is a successful no-op. Release commits use `[skip ci]`.
- Builds are reproducible; Python prerelease filenames use PEP 440 spelling while Git tags retain theirs.

## Workflows and repository setup

| Workflow           | Trigger / work                                                            |
|--------------------|---------------------------------------------------------------------------|
| `ci.yml`           | Branch pushes and PRs: title, static/docs and platform checks             |
| `main-release.yml` | Main push or manual run on main: checks, release/recovery and tagged docs |

Enable Actions write permission and configure Pages to publish from `gh-pages`.
The first approved docs deployment creates that branch. CI summaries distinguish no release,
failed/skipped checks and incomplete publication.
