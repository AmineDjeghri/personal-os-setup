# 3. Conventions

The rules every change follows.

## Code

- Python, ruff (format and lint), Google docstrings: they generate the API reference
  (mkdocstrings).
- Run things with `make` targets (`make help`): CI runs the same ones.
- Logging with loguru (`from loguru import logger`). Log, then raise:

    ```python
    if not path.exists():
        logger.error(f"File not found: {path}. The current directory is: {Path.cwd()}")
        raise FileNotFoundError(path)
    ```

    In a loop, log and continue instead of raising when one failure must not stop the others.

- System-changing actions (installs, `chezmoi apply`, drivers, `sudo`) always go through the
  TUI's confirmation dialog.
- Use uv for everything (environments, runs, builds). For large data, Polars; for CPU-bound work,
  a `multiprocessing` pool.

## Branches and pull requests

1. Comment on (or create) the issue and wait to be assigned.
2. Branch off `dev`: `feature/<name>` or `bugfix/<name>`. Stay up to date with `git merge dev`
   (branch already pushed) or `git rebase dev` (local only).
3. Run `make check` ([4. Testing](4.testing.md)), then open a pull request to `dev`; its **title** follows the commit convention below: it becomes the
   squash commit and decides the version.
4. When `dev` is ready, a pull request `dev` → `main` releases it.
5. After a release, merge `main` back into `dev` (merge commit, direct push). On conflicts on
   `CHANGELOG.md` or a `pyproject.toml` version, keep `main`'s and regenerate `uv.lock` with `uv lock`.

| Merge                 | Strategy                  | Why                                                  |
| --------------------- | ------------------------- | ---------------------------------------------------- |
| `feature/*` → `dev`   | squash                    | one conventional commit per feature                  |
| `dev` → `main`        | squash                    | one commit for semantic-release to evaluate          |
| `main` → `dev` (sync) | merge commit, direct push | sync stable metadata without a new releasable commit |

Never edit a version in `pyproject.toml` or create a tag by hand: semantic-release does both.

## Commit convention

`[emoji] <type>[(<scope>)][!]: <description>`, the emoji is optional ([Gitmoji](https://gitmoji.dev/)).

| Emoji                | Type                                                        | Aliases                   | Release |
| -------------------- | ----------------------------------------------------------- | ------------------------- | ------- |
| 🐛                   | `fix`                                                       | `bugfix`, `hotfix`        | patch   |
| ⚡️                   | `perf`                                                      |                           | patch   |
| ✨                   | `feat`                                                      | `feature`                 | minor   |
| 💥                   | `feat!`                                                     | `BREAKING CHANGE:` footer | major   |
| ♻️ 📝 🎨 🧪 🔧 👷 📦 | `refactor`, `docs`, `style`, `test`, `chore`, `ci`, `build` |                           | none    |

```text
✨ feat(auth): add GitHub App token rotation
🐛 fix(llm): handle empty response from the API
💥 feat!(api): remove the v1 endpoint

feat(auth): redesign token flow

BREAKING CHANGE: /v1/token removed, use /v2/auth instead
```

Scopes are optional.

On `dev`, a releasable commit bumps the release candidate instead (`1.1.0-rc.1` → `1.1.0-rc.2`).

Common scopes: `tui`, `wsl`, `chezmoi`, `frontend`, `ci`, `deps`. The commit message is checked on
commit (commitizen) and the pull request title by `ci.yml`.

## Secrets

- Never write a credential to a file of this public repository, even untracked; use environment
  variables or `gh auth login`.
- `detect-secrets` runs on commit. For a line that intentionally references a secret placeholder (`${{ secrets.X }}`),
  add `# pragma: allowlist secret`. Keep suppressions inline; never exclude a whole file to silence one line.

## Environment variables

Adding, renaming or removing one, in the same change: the setting in `settings.py` if the app
reads it, `.env.example` if a laptop needs it, and the workflow `env:` if CI needs it.
Update the [release credentials](5.release.md#credentials) if a release target reads it.

## Dependencies (Renovate)

Renovate (`.github/renovate.json`) opens pull requests to `dev` with the `renovate` and `dependencies` labels; most routine
updates have a 7-day cooldown; security fixes are not grouped and open at once. Runtime dependencies include exact pins and ranges;
`uv.lock` makes builds reproducible. Review every Renovate pull request; a dependency dashboard
issue lists the pending ones.

1. Renovate does not widen the Python range. The supported interpreter moves by hand, together with
   the CI action and this document.
2. PyPI updates use strict Python compatibility filtering. Weekly lockfile maintenance refreshes
   versions already permitted by dependency ranges; review the lockfile and CI results too.
3. Renovate updates dependency files, GitHub Actions and pre-commit revisions; update README
   and developer documentation when the supported Python range changes. Docs are not rewritten
   automatically.
4. Renovate tracks the Node pin used by pre-commit. Stable updates wait seven days and use
   `chore`; major upgrades require dependency dashboard approval.
